# dsh-session-vault（会话位置）

一个非官方的 DeepSeek Harness 插件：决定 **DSH 把对话存在哪里**——本机默认目录，或你指定的任意文件夹（U 盘、移动硬盘、网络盘）。

切换是**路径重定向**，不是搬迁：DSH 直接读写那个文件夹。运行期间不复制、不改名、不移动、不删除任何东西；复制是一个单独的、你点了才发生的按钮。

> English: [README.md](README.md)

## 兼容性

在 **DeepSeek Harness 44.7.0**（Electron，自带 Node 24.21）+ Windows 11 上验证。整套测试就是跑在 DSH 自带的那份运行时上（Electron 44.7.0 / Node 24.21.0 / V8 15.2），不只是系统 Node——所以 `node:zlib`、`fs.realpath`、`process.getBuiltinModule` 都是插件真正会拿到的那一版。

它读的是 DSH 自己的格式——工作区索引（`workspace` v2）和会话日志（`session.v4.jsonl.zstd`），所以 DSH 升级有可能把它弄坏。每个破坏性命令都会先探测这些版本，遇到比本插件新的库就拒绝；`/vault check` 打印同一份报告。换单位（迁移）只接受 v4 日志：更老的会话可以在原地打开，但它的记录不会被转换。`.cmd` 急救脚本和锁的 PID 判断是 Windows 专有；macOS / Linux 未验证。

## 它改的是什么

`custom` 模式下，Loader 补丁把三个根指到选定文件夹：

| 根 | 本机默认 | 指定文件夹 |
|---|---|---|
| `sessions` | `%USERPROFILE%\.dsh\sessions` | `<库>\sessions` |
| `storages` | `%USERPROFILE%\.dsh\storages` | `<库>\storages` |
| `attachments` | `%USERPROFILE%\.dsh\attachments` | `<库>\attachments` |

本机 `.dsh` 仍保留：模式记录、profile/插件、凭据、日志、急救脚本。**指定文件夹模式下，对话正文、投影缓存、附件都不落本机。**

## 安装

用 Plugin Manager 安装这个仓库（或 link），或在 profile 的 `package.json` 里加：

```json
"dependencies": { "dsh-session-vault": "github:wodebilu/dsh-session-vault" }
```

本地开发可以 link 一个 checkout：

```json
"dependencies": { "dsh-session-vault": "link:/absolute/path/to/dsh-session-vault" }
```

启用 bundle 后**完全退出 DSH 再打开**。控件在侧栏底部、**头像/设置按钮上方**那一条。

## 迁移会话（1.2.0）

侧栏底部面板新增**迁移会话**：选源会话、目标库（当前库或另一个文件夹）、
目标工作区（空文件夹也可以）、新标题；先预览，再执行。

迁移会完整克隆历史，一条记录写一个 zstd 帧，同时改写投影缓存和 ISO-8601
Workspace 索引；源会话只读，不删不移。通过 `lib/zstd-frames.mjs`，在 DSH
自带的 Node 24.21 上也能读多帧日志。

命令形式：`/vault migrate <b64-json>`（面板会自动拼好载荷）。
迁移后重启一次 DSH，新工作区才会出现。

## 简单面板（1.3.0）

侧栏面板改成 4 个按钮：**切换存储位置 / 回到本机默认 / 管理会话 / 新手教程**。

“管理会话”里有 4 项：3 个操作 + 备份与恢复。

1. **搬家：换库，不改工作区** —— 会话日志、投影缓存、附件、子会话一起搬到另一个库；
   header 的 `cwd` 不变，侧栏里仍属于原工作区。目标库会自动建/复用同路径工作区。
2. **换单位：换工作区** —— 改 `cwd`，工具去新项目跑；日志、缓存、附件、子会话一起走；
   库可不变，也可以一起搬。
3. **删除会话** —— 先备份到 `_deleted/<时间>-<id>`，再删索引、日志、缓存和子会话；
   附件默认保留（可能被别的会话共用）。

默认是**复制**；只有显式勾选“移动并删除源”才会删源，且删前备份。技术项（索引修复、
复制、状态、路径）收进“高级”。

命令：`/vault copy <b64-json>`、`/vault migrate <b64-json>`、`/vault delete <b64-json>`、
`/vault drop-backups <b64-json>`、`/vault cleanup`。

### 备份与恢复（1.3.0）

删除会话、搬家、换单位都会把源备份到 `<库>\_deleted\<时间>-<会话id>\`。
“管理会话 → 备份与恢复”可以查看备份地址、恢复会话、删除备份；恢复会带回日志、
缓存和子会话树；原 id 已存在时生成新 id；删备份只删 `_deleted`，不碰活动会话。

### 备份会越堆越多，所以可以清理（1.4.0）

一份备份里是：日志、它的投影缓存、索引，以及一个小的 `backup.json`。**不再包含附件**
——附件是会话之间共用的，删除和搬家从不删活动附件，所以把整个附件库复制进每份备份
只是纯冗余（删 N 次 ≈ N × 附件总量）。1.3.0 时代带附件的旧备份仍然能正常恢复。

备份弹窗里的“保留最近 N 份”会清掉其余的；填 `0` 就是全删。只会删 `_deleted` 下
的目录，散在里面的普通文件不会被动。

## 用法

- **会话位置**（侧栏底部）：显示当前根目录、选定文件夹是否可用。
- **选择文件夹…**：先把文件夹准备成可用的库（清单 + 有效工作区索引），再写模式记录；切换失败不会把 DSH 扔在坏状态里。重启生效。
- **用回本机默认**：写入 `{"mode":"default"}`，清掉急救标记；路径仍记着，复制按钮还要用。重启生效。
- **复制到指定文件夹 / 复制回本机**：显式、只增不删。目标已存在就跳过；正在变长的文件重试后跳过；来源只读。
- **修复索引**：把库里的 `workspace.json` 规范回来——所有工作区都登记、同路径的合并、默认工作区有效。不碰任何会话文件。

## 为什么有开机守卫

1.0 会把 DSH 切到一个**没有工作区索引**的文件夹。于是 DSH 没有工作区、也建不出会话；而唯一能切回去的 `/vault` 命令，必须挂在一个已打开的会话上。这就是死锁：**修它的按钮，要求它没坏**。最后只能重装。

1.1 用四层堵住：

1. **先准备，再切换。** `useCustom` 在写模式记录之前就把索引建好；切换失败不会留下坏状态。
2. **开机先准备，准备不了才拒绝。** Loader 表达式只用它能真正准备好的文件夹：不存在就建，空就 seed 一个 Vault 工作区和有效索引；只有建不了、用不了才让三个根全部回退本机默认。决策写进 `session-vault-boot.log`。
3. **不需要会话的急救。** Host 半边每次启动都会留下 `%USERPROFILE%\.dsh\恢复本机.cmd`（以及 `session-vault-recover.cmd`）。双击它：写 `{"mode":"default"}`，再放一个 `session-vault.panic` 标记，下一次启动强制用本机默认——哪怕界面根本打不开。
4. **UI 不再重叠。** 控件住在 `sidebar.footer.action`，不再是盖在头像上的固定胶囊。

指定文件夹不可用时，DSH 会用本机默认启动，面板会明确告诉你。对话还在那个文件夹里，修好或切回去即可。

## 急救顺序

1. 侧栏面板还能开 → 点「用回本机默认」→ 重启。
2. 面板打不开 → 双击 `%USERPROFILE%\.dsh\恢复本机.cmd` → 完全退出 DSH 再打开。
3. DSH 根本起不来 → 手动建一个空文件 `%USERPROFILE%\.dsh\session-vault.panic`，再启动。恢复后在面板里选一次模式即可清掉它。

## 状态

`1.5.0` 是当前版本：只做路径重定向，启动前建好/修好工作区索引，把没有归属的会话日志收养进工作区，并附带一套不需要打开会话的急救包。除非你明确要求搬家或删除，它不会移动、改名或删除会话文件；这两种操作都会先备份源。

1.4.0 加了备份清理、库锁和本地日志清理；1.5.0 打磨了复制引擎（子会话树单次遍历、工作区路径规范化、按代次复制），并补了 DOM 与启动测试以及 CI。1.4.0 里那个"导出干净对话"在 1.5.0 **被移除了**：把对话从 DSH 里读出来是另一件事，该由独立插件做。

> **不要再用 0.x。** 0.x 把 `.dsh` 目录换成了 Junction，这一版正是把那套设计删掉。请直接升级，不要混装。

「任意跨工作区分组（集合/标签）」和「按会话复制/剪贴」不在这一版里，留到下一版。

### 格式闸门

`copy`、`delete`、`migrate`、`restore` 这四个破坏性命令，动手前都会先探测库里 DSH 实际写下的工作区索引版本和会话日志代次。只要其中哪个**比本插件新**，命令就会被拒绝并说明原因，而不是按旧格式写进新库里。`/vault check` 会打印同一份报告。

## 诚实的限制

- **同一个库同时只开一个 DSH。** `<库>\.dsh-session-vault.lock` 记录占用它的进程：Host 半边启动时拿锁、卸载时放锁，持有者已死则自动接管，`status.lock` 会报告。另一个活进程持锁时，面板会明确提示，`copy`/`delete`/`migrate`/`restore`/`drop-backup(s)`/`push`/`pull` 都会被拒绝。这是忠告式的守卫：它拦不住 DSH 启动。
- **日志能走，工作目录不能走。** 工作区绑定的是会话的 `cwd`。要做到真正便携，项目文件夹和库要放在**同一块可移动盘**上，并在每台机器上固定同一个盘符（例如 `F:`）。如果 `cwd` 是本机路径、第二台机器上没有这个目录，历史仍然能读，但工具跑不起来，那个工作区里也无法新建会话。固定盘符或挂载点是每台机器各自的设置；本插件不改写这类 `cwd`（见下一节）。

## 换了一台机器之后

会话库跟着 U 盘走，但**记录里的路径是一台机器上的绝对路径**：工作区索引的 `path`、会话分组目录名、每个会话 header 的 `cwd`。换机后 DSH 会按 header 的 `cwd` 重新推导日志位置，对不上就报 `corrupt session log … and cwd identify …`，或者在工作区里直接 `ENOENT`。

插件的核心能力就是**修盘符**：U 盘插到不同机器上盘符本来就不固定，记录里的路径必须跟着库所在盘一起换算。

| 情况 | 插件做什么 |
|---|---|
| 工作区记录的是一个**别的盘符**（U 盘上次是 `E:`，这次是 `F:`） | **启动时自动换算**：索引 `path`、会话分组目录名、每个 header 的 `cwd` 一起改成库所在的盘。原文件先备份到 `<库>\_drift-backup\<时间>\` |
| 换算后目录还不存在 | 照常换算（DSH 第一次用时会建），同时提醒你确认项目真的在那个位置 |
| 盘符**没变**，但目录不存在（另一台电脑的用户目录、改名/移走的项目） | **不改写**，报告出来。盘符没变说明项目没跟着库走，只能 `/cd` 重新指路 |
| 记录的就是库当前盘符，只是这个盘没接上 | 什么都不改（改了也没有变化），报告"盘符没接上" |
| 一切正常 | 什么都不做，也不写盘 |

**换机不需要任何操作：插上 U 盘、打开 DSH，就能接着用。** 换算在 Host 半边启动时完成，结果写进
`status().drift`（`applied` / `changes` / `backup`）和 `session-vault-fallback.log`。

两条约束：

1. **只在库空闲时改。** 启动时会先拿库锁；如果另一个 DSH 进程正持有这个库，改写会被推迟
   （`status().drift.deferred = 'library in use'`），关掉那个窗口再启动即可。改写时 DSH 正可能往
   同一批日志追加，这是唯一不能让步的条件。
2. **改之前一定先备份。** 索引和每个被改写的日志原件都在 `<库>\_drift-backup\<时间>\`，附 `repair.json`。

出问题时的应急路径（平常不需要）：

- 想先看会改什么、暂不执行：`/vault drift` 只返回计划。
- 手动重跑一次：`/vault drift-fix confirm`（需要在库空闲时）。
- 换机后个别工作区显示"目录不存在"：那是盘符没变的情况，用 `/cd` 或面板的「换单位」指到真实目录。

> 也可以在两台机器上把这块盘固定成同一个盘符（Windows 磁盘管理 → 更改驱动器号）。不固定完全没问题——
> 这只是一种可选的习惯，不是前提。

- **不加密。** U 盘丢了，等于对话库丢了。
- **元数据仍在本机。** 模式记录、启动日志、急救包、profile、凭据都在 `.dsh`。
- **不是备份。** 复制是单向、按需的，不做同步，也不会镜像删除。

## 测试

`npm install && npm test` 用 DSH 自带的 Node 24.21（或任何 >= 22.3 的 Node）跑整套测试（65 个用例）。它在 `test/.tmp` 下建临时库，不碰 `~/.dsh`。`--test-isolation=none` 是有意的：DSH 的沙箱 shell 里测试运行器起不了子进程，关掉隔离才能跑通。

`test/client-dom.test.mjs` 按 DSH 的方式加载 `client.js`（假模块加载器 + 真 React），在 jsdom 里挂载侧栏控件，再把面板点一遍：切换位置、备份清理、日志清理、锁警告。它证明的是 React 树和发给 Host 的载荷，不是 DSH 外壳的排版。
